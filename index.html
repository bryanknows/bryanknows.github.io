Case study: how the Hub came together
The problem
Sales, housing, and accounting each kept their own spreadsheets, fed by the same property management reports. The same question ("how many new leases this month?") got a different answer in each one, because each sheet counted renewals and transfers its own way.
My part
I designed and built the whole platform on my own while carrying a full leasing workload: the data model, the sync functions, the SQL views, the front end, and the SOPs the team uses to run it.
Architecture
  • Postgres on Supabase holds applications, units, leases, tenants, leads, and showings. Auth gates every page so hub links can't be opened by anyone outside the team.
  • About 23 edge functions pull property management reports on a schedule, compute availability, and load the rent roll.
  • Business rules live in SQL views, so every department's dashboard counts the same way. Change the rule once and every screen updates.
  • Next.js and React front end with one section per department, deployed on Netlify.
Hard decisions
  • A lease-type taxonomy that separates genuinely new business from renewals and transfers. Before it, leadership couldn't tell the two apart in the numbers.
  • Moving the data source from emailed CSV exports to the property management system's reports directly, so the Hub refreshes without anyone forwarding a file.
  • Keeping a Google Sheets two-way sync for the one team that still works in a sheet, instead of forcing everyone onto the Hub at once.
Results
Five to ten people use it daily. One number per question across departments, and leadership's monthly new-business, renewal, and transfer counts now come from one view instead of three reconciled spreadsheets.
Lessons
Put the rule in the database, not the dashboard. Migrate one department at a time. Write the SOP before calling the tool done.

Case study: from report export to availability view
The problem
AppFolio reports arrived as emailed exports. Someone opened each one, pasted it into a sheet, fixed the columns, and rebuilt the leadership numbers by hand. During showings, agents cross-referenced three different date fields to answer "is this unit available, and from when?"
My part
Built the import system, the per-property dashboards, the executive roll-up, and the availability view. About 5,800 lines of Apps Script, written and maintained by me.
How it flows
  • Scheduled job finds the newest report exports and pulls them into a raw tab, untouched.
  • Cleanup step normalizes property and unit names so every report agrees on what a unit is called.
  • Calculated fields derive one availability date per unit from the three date fields that used to be checked by hand.
  • Per-property dashboards update from the clean data, and the highlights roll into one executive view.
  • The availability view lists open and upcoming units across 283 units, plus an occupancy timeline for one building, and refreshes on the same schedule as the dashboards.
Hard decisions
  • Keep the raw export untouched and do every fix in a separate step, so a bad report can be re-run without losing work.
  • Let the team keep their own layout, column widths, and notes across refreshes. The first version wiped them, and nobody used it.
  • Chain the refreshes: when the main dashboard updates, the availability view updates right after, instead of on its own timer.
What it looks like
Results
Reports update on a schedule with a manual refresh button for anything urgent, and the leadership numbers no longer depend on one person pasting. Agents answer availability questions from one column.
Lessons
Normalize names before anything else. Never overwrite what the user typed. A refresh that runs on time beats one that's technically better but nobody trusts.
